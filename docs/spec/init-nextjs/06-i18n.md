# i18n — next-intl

Internationalization with **next-intl 4.x**: the App Router-native library — translations work in
Server AND Client Components, locale-prefixed routing (`/vi/events`), per-feature message
namespaces, and type-safe keys via TypeScript augmentation. Even a single-language app uses
`t()` from day one — retrofitting i18n is the most expensive refactor in frontend
(`01-architecture-principles.md` §8).

## 1. Wiring — `src/i18n/` + proxy + layout

```ts
// src/i18n/routing.ts
import { defineRouting } from 'next-intl/routing';
export const routing = defineRouting({
  locales: ['en', 'vi'],
  defaultLocale: 'vi',
  localePrefix: 'as-needed',      // default locale unprefixed; /en/... for the rest
});
```

```ts
// src/i18n/request.ts — per-request config: load ONLY the namespaces… (see §2)
import { getRequestConfig } from 'next-intl/server';
import { routing } from './routing';

export default getRequestConfig(async ({ requestLocale }) => {
  const requested = await requestLocale;
  const locale = routing.locales.includes(requested as any) ? requested! : routing.defaultLocale;
  return { locale, messages: (await import(`../../messages/${locale}.ts`)).default };
});
```

```ts
// src/i18n/navigation.ts — the ONLY navigation API features may use
import { createNavigation } from 'next-intl/navigation';
import { routing } from './routing';
export const { Link, redirect, usePathname, useRouter, getPathname } = createNavigation(routing);
```

- Locale routing runs in `src/proxy.ts` — compose next-intl's middleware with the auth check
  (`05-auth-google.md` §5): locale resolution first, then the optimistic auth redirect.
- The app moves under `app/[locale]/` (route groups inside it: `[locale]/(public)/`,
  `[locale]/(app)/`); the root layout reads `params.locale`, calls `setRequestLocale`, sets
  `<html lang>`, and wraps client children in `<NextIntlClientProvider>`.
- The plugin line in `next.config.ts`: `withNextIntl` (`next-intl/plugin`) pointing at
  `src/i18n/request.ts`.

Decisions encoded here:

| Choice | Why |
| --- | --- |
| Locale in the URL (`[locale]` segment) | SEO for the public pages (each language indexable, `hreflang` via metadata), shareable links, and server rendering knows the locale without a cookie roundtrip. |
| `localePrefix: 'as-needed'` | The default language keeps clean URLs; others get a prefix. Flip to `'always'` if analytics/SEO prefer symmetry. |
| Namespace == feature | `messages/<lng>/<feature>.json` belongs to the feature slice (`02-folder-structure.md` §2): change a feature, change only its namespace. `common` holds shared chrome (buttons, validation, nav). |
| Messages aggregated per locale (`messages/<lng>.ts` re-exporting the JSONs) | next-intl loads messages per REQUEST server-side — no lazy-HTTP machinery needed; the server sends client components only what the provider passes. Keep the aggregate file mechanical (one import line per namespace). |

## 2. Usage in Features

**Server component** (lists, pages, metadata):

```tsx
// features/events/server/… or a thin page
import { getTranslations } from 'next-intl/server';
const t = await getTranslations('events');
<PageHeader title={t('list.title')} />
```

**Client component**:

```tsx
// features/events/components/event-list.tsx ("use client")
import { useTranslations } from 'next-intl';
const t = useTranslations('events');
<EmptyState message={t('list.empty')} action={t('list.createFirst')} />
```

- The namespace argument (`useTranslations('events')`) scopes keys — cross-namespace access is a
  different call (`useTranslations('common')`), kept explicit.
- **Interpolation & plurals through ICU MessageFormat, never string concatenation:**

```json
// messages/en/events.json
{
  "list": {
    "title": "Events",
    "count": "{count, plural, =0 {No events} one {# event} other {# events}}"
  },
  "form": { "errors": { "capacityPositive": "Capacity must be greater than zero" } }
}
```

```tsx
t('list.count', { count: events.length })
```

- Dates/numbers/currency: `useFormatter`/`getFormatter` from next-intl (or `Intl` via
  `lib/format.ts` fed with the active locale) — not hand-formatted strings, not locale data
  duplicated into JSON.
- Zod form messages are **keys** resolved at render (`03-ui-layer.md` §4): the schema says
  `'events.form.errors.capacityPositive'`, `<FormMessage>` runs it through `t()` (the one-line
  FormMessage tweak from 12 Phase 2 — the stock shadcn component renders raw text).
- **Metadata is translated too**: `generateMetadata` uses `getTranslations` — the `<title>`
  changes language with the page (`07-rendering-caching.md` §5).

## 3. Type-Safe Keys

Augmentation gives compile-time key checking and editor autocomplete (next-intl's documented
pattern):

```ts
// src/types/i18n.d.ts (or global.d.ts)
import type messages from '../../messages/en';

declare module 'next-intl' {
  interface AppConfig {
    Locale: 'en' | 'vi';
    Messages: typeof messages;
  }
}
```

- The **default locale's catalog is the schema** (`en` above; a vi-first product imports
  `messages/vi` and the parity check compares against `vi`): a typo'd key or missing namespace
  becomes a TS error, not a raw key string in production.
- Typed `Locale` means a `[locale]` route param (`string`) no longer fits `getTranslations({ locale })`
  / `setRequestLocale` — narrow it once in a kernel helper (`src/i18n/locale.ts`:
  `hasLocale(routing.locales, v) ? v : notFound()`) and call that from layouts, pages and
  `generateMetadata`; never cast. `request.ts` uses the same `hasLocale` instead of `includes(x as any)`.
- Adding a feature = one import line in `messages/<lng>.ts` per language (the plop feature
  generator does it — `08-ai-agent-first.md`).
- Guard against drift between languages with a CI check (compare key sets of `en/*` vs other
  languages — the locale-parity check in `scripts/check-architecture.sh`).

## 4. Language Switching & Navigation

```tsx
// components/layout/language-switcher.tsx (kernel — product-agnostic chrome, "use client")
import { usePathname, useRouter } from '@/i18n/navigation';
const router = useRouter(); const pathname = usePathname();
router.replace(pathname, { locale: nextLocale });   // same page, other locale
```

- **All navigation in features goes through `src/i18n/navigation.ts`** (`Link`, `useRouter`,
  `redirect`) — plain `next/link`/`next/navigation` drops the locale prefix. Lint-banned in
  features (`08-ai-agent-first.md` §3b).
- next-intl persists the choice (locale cookie) and sets alternate links; also ensure
  `generateMetadata` emits `hreflang` alternates for public pages.
- Content from the API is the backend's concern (`Accept-Language` can be forwarded in the
  mutator if the API localizes) — do not translate server data client-side.

## 5. Smells — agent self-check

- Hardcoded user-facing strings in JSX (the `t()` rule exists from day one, even single-language).
- String concatenation for sentences (`t('hello') + name`) instead of ICU interpolation — breaks
  under word-order differences.
- Manual plural branching (`count > 1 ? 's' : ''`) instead of ICU `plural`.
- A feature's strings landing in `common.json` (namespace = feature, keep the slice closed).
- New namespace not added to the per-locale aggregate + the `en` schema (silently untyped keys).
- `next/link` or `next/navigation` imported in a feature instead of the `i18n/navigation` wrappers.
- `getTranslations` awaited inside a client component, or `useTranslations` in a server file —
  wrong side of the boundary.
- Locale-specific formatting hand-rolled (`toFixed`, manual date strings) instead of the
  formatter APIs.
- Public pages whose `generateMetadata` ignores the locale (same English `<title>` on `/vi/...`).
