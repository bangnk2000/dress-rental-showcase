# i18n — react-i18next

Internationalization with **i18next + react-i18next** (i18next 26.x / react-i18next 17.x):
per-feature namespaces, lazy-loaded translation files, detected + persisted language, and
type-safe keys via TypeScript module augmentation. Even a single-language app uses `t()` from day
one — retrofitting i18n is the most expensive refactor in frontend (`01-architecture-principles.md` §8).

## 1. Initialization — `lib/i18n.ts`

```ts
import i18n from 'i18next';
import { initReactI18next } from 'react-i18next';
import HttpBackend from 'i18next-http-backend';
import LanguageDetector from 'i18next-browser-languagedetector';

i18n
  .use(HttpBackend)                    // lazy-load /locales/<lng>/<ns>.json per namespace
  .use(LanguageDetector)               // querystring → localStorage → navigator
  .use(initReactI18next)
  .init({
    fallbackLng: 'en',
    supportedLngs: ['en', 'vi'],
    defaultNS: 'common',
    ns: ['common'],                    // feature namespaces load on demand via useTranslation
    interpolation: { escapeValue: false },  // React already escapes
    backend: { loadPath: '/locales/{{lng}}/{{ns}}.json' },
    detection: { caches: ['localStorage'] },
  });

export default i18n;
```

Imported once in `main.tsx` (side-effect import) **before** the app renders; the provider wiring in
`app/providers.tsx` is just React's context (`I18nextProvider` is optional when using the singleton,
but keep it explicit for tests).

Decisions encoded here:

| Choice | Why |
| --- | --- |
| `i18next-http-backend` + `public/locales/` | Translations are static assets, lazy-loaded per language+namespace — they never enter the JS bundle. Bundled `resources` are acceptable only for a trivial single-namespace app. |
| Namespace == feature | `public/locales/<lng>/<feature>.json` belongs to the feature slice (`02-folder-structure.md` §2): change a feature, change only its namespace. `common` holds shared chrome (buttons, validation, nav). |
| LanguageDetector with localStorage cache | URL `?lng=` beats stored choice beats browser locale; the user's explicit pick persists. |
| `escapeValue: false` | Standard for React — double-escaping garbles text; React handles XSS at render. |

## 2. Usage in Features

```tsx
// features/invoices/components/invoice-list.tsx
const { t } = useTranslation('invoices');        // suspends until the namespace is loaded
...
<PageHeader title={t('list.title')} />
<EmptyState message={t('list.empty')} action={t('list.createFirst')} />
```

- `useTranslation('<feature>')` declares the namespace dependency and (with React Suspense — the
  default) suspends until it is fetched: the route-level `<Suspense>` from the data layer
  (`04-data-layer.md` §5) covers this too — one fallback, two concerns.
- Cross-namespace access is explicit: `t('common:actions.save')`.
- **Interpolation & plurals through i18next, never string concatenation:**

```json
// public/locales/en/invoices.json
{
  "list": { "title": "Invoices", "count_one": "{{count}} invoice", "count_other": "{{count}} invoices" },
  "form": { "errors": { "amountPositive": "Amount must be greater than zero" } }
}
```

```tsx
t('list.count', { count: invoices.length })     // picks _one/_other automatically
```

- Dates/numbers/currency: `Intl` via `lib/format.ts`, fed with `i18n.language` — not hand-formatted
  strings, not locale data duplicated into JSON.
- Zod form messages are **keys** resolved at render (`03-ui-layer.md` §4): schema says
  `'invoices:form.errors.amountPositive'`, `<FormMessage>` runs it through `t()` (requires the
  one-line `FormMessage` tweak from 12 Phase 2 — the stock shadcn component renders raw text).

## 3. Type-Safe Keys — `types/i18next.d.ts`

Module augmentation gives compile-time key checking and editor autocomplete (the officially
documented pattern):

```ts
// src/types/i18next.d.ts
import type common from '../../public/locales/en/common.json';
import type invoices from '../../public/locales/en/invoices.json';

declare module 'i18next' {
  interface CustomTypeOptions {
    defaultNS: 'common';
    resources: {
      common: typeof common;
      invoices: typeof invoices;
    };
  }
}
```

- `resolveJsonModule: true` in `tsconfig.json` makes the JSON imports typed.
- The **English files are the schema**: every namespace registers here; a typo'd key or a missing
  namespace becomes a TS error, not a blank string in production.
- Adding a feature = adding one line here (the plop feature generator does it —
  `08-ai-agent-first.md`).
- Guard against drift between languages with a CI check (compare key sets of `en/*` vs other
  languages — a 20-line script in `scripts/check-architecture.sh` or i18next-parser).

## 4. Language Switching

```tsx
// components/layout/language-switcher.tsx (kernel — it's product-agnostic chrome)
i18n.changeLanguage(lng);              // http-backend fetches missing namespaces automatically
```

- Persisting is automatic (detector cache). Also set `<html lang>` on change
  (`document.documentElement.lang = lng`) for a11y/SEO.
- Content from the API is the backend's concern (`Accept-Language` header can be added in the
  mutator if the API localizes) — do not translate server data client-side.

## 5. PWA interaction

Translation JSONs are static assets: include `public/locales/**` in the service worker's
**runtime** caching (StaleWhileRevalidate), not precache — precaching every language bloats the
install; see `07-pwa.md` §3.

## 6. Smells — agent self-check

- Hardcoded user-facing strings in JSX (the `t()` rule exists from day one, even single-language).
- String concatenation for sentences (`t('hello') + name`) instead of interpolation — breaks under
  word-order differences.
- Manual plural branching (`count > 1 ? 's' : ''`) instead of `_one/_other` keys.
- A feature's strings landing in `common.json` (namespace = feature, keep the slice closed).
- New namespace not registered in `types/i18next.d.ts` (silently untyped keys).
- Locale-specific formatting hand-rolled (`toFixed`, manual date strings) instead of `Intl` helpers.
- Translations imported into the bundle (`import en from ...` fed to `resources`) in a multi-feature
  app — kills the lazy-loading the http-backend exists for.
