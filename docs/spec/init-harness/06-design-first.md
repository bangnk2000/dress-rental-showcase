# Design-First Loop — Intent Before Implementation

The five subsystems (01) verify that work was done *correctly*. This file adds the layer above:
deciding *what to build* before code makes the decision expensive. It is stack-agnostic; the
concrete design-doc templates come from the stack init's binding
([05-composition-contract.md](./05-composition-contract.md) — the optional `DESIGN_TEMPLATE`
slot; `init-nestjs-hexagonal/14-design-first.md` and `init-react/14-design-first.md` are the
worked bindings).

The principle: **pay for design where changing your mind later is expensive; iterate freely
where it is cheap.** Aggregate boundaries, cross-context contracts, navigation structure, and
data-consistency rules are expensive to change after code exists. Wording, styling, and query
tuning are cheap. Design docs cover the first kind only.

## 6.1 Two Kinds of Docs — Intent vs Truth

Every document in the repo is exactly one of these, and the rules differ:

| Kind | Examples | Written | Kept honest by |
| --- | --- | --- | --- |
| **Intent** (why / what-should-be) | Requirements brief (SRS), tactical design docs, ADRs, UX flows | By hand, BEFORE the code they govern | Review before code + an as-built re-sync after merge |
| **Truth** (what-is) | Generated architecture map / inventory, generated API contract (`openapi.json`), generated client | By script, FROM the code | A `*:check` CI gate: regenerate + `git diff --exit-code` |

Rules:

- **Anything derivable from the disk is generated, never maintained by hand.** A hand-maintained
  inventory is stale by the third session; a generated one cannot lie.
- **An intent doc never restates what a truth doc generates.** It records decisions and their
  *why* — the parts no script can recover from code.
- **Intent docs carry a date and an as-built note.** After the feature merges, reconcile the doc
  with what was actually built (one dated line is enough: "as-built 2026-07-02, matches" or
  "deviated: <what> because <why>"). An intent doc with no reconciliation and no date is a rumor.

## 6.2 The Artifacts

| Artifact | Scope | When written |
| --- | --- | --- |
| Requirements brief / SRS | Product or phase | Once per product/phase, before any design doc |
| Tactical design doc | One bounded unit (context/aggregate for a backend, feature slice for a frontend — the binding defines the unit) | Before the unit's first design-tier feature |
| ADR | One cross-cutting decision | When the decision is made — including "deviate from the spec" decisions |
| Truth docs | Whole repo | Generated by script; wired into CI with a check gate at bootstrap |

Store intent docs in the repo (`docs/design/`, `docs/adr/`), next to the code they govern — not
in a wiki that drifts independently.

## 6.3 Design Tiers — not everything earns a doc

Calibrate per feature, and say which tier you chose (mirror of the sizing tiers in 01 §3):

| Tier | Criteria | Required design artifact |
| --- | --- | --- |
| **Mechanical** | Rename, dependency bump, bugfix inside one file | None — the `feature_list.json` description is enough |
| **Standard** | CRUD-shaped feature on existing patterns | The stack scaffold prompt's INPUT CONTRACT, fully filled — that filled block IS the mini design doc; attach or link it in the feature entry |
| **Design-tier** | New aggregate/bounded unit, new invariant, new cross-context contract, new navigation/interaction pattern, anything concurrency-sensitive | Full design doc per the binding's `DESIGN_TEMPLATE`, reviewed BEFORE implementation starts |

The gate (extends the session loop in [03-session-loop.md](./03-session-loop.md)): a
design-tier feature may not move to `in-progress` until its design doc exists and was approved.
Writing the doc is itself legitimate session work — a session that produces only a reviewed
design doc is a successful session.

## 6.4 The Loop

```
DESIGN     → write/update the unit's design doc (tier says how much) → review/approve
IMPLEMENT  → the normal session loop (03) — the design doc is in-scope context every session
RE-SYNC    → after merge: as-built note on the design doc; new decisions → ADR;
             truth docs regenerate via their check gates (automatic)
```

Two failure modes this ordering prevents:

- **Design after code** — a doc written to describe what was already built is paperwork, not
  design; it caught nothing. If you find yourself doing this, the feature was mis-tiered.
- **Design without re-sync** — implementation always teaches something. A doc that was right at
  review time and never reconciled becomes misinformation with authority.

## 6.5 The Invariant Rule (applies to every design-tier doc)

Every critical invariant identified at design time MUST name, in the design doc:

1. **Where the system physically refuses to violate it** — not just where code checks politely.
   For a database-backed system that means a constraint; for a frontend that means the state
   machine that makes the invalid action unreachable. "The handler checks first" is not an
   enforcement layer; it is a courtesy message.
2. **The proof** — the automated test that provokes the violation and observes the refusal.

A design doc that lists invariants without enforcement + proof columns is incomplete. The stack
bindings define the concrete mechanics (DB constraints and race-condition tests for the backend;
unreachable-action state machines for the frontend).

## 6.6 Smells

- A design-tier feature `in-progress` with no design doc — the tier gate was skipped.
- A design doc that restates the generated inventory/contract — intent duplicating truth.
- A truth doc maintained by hand, or one without a CI check gate — it is already stale.
- Design docs with no dates and no as-built notes — unfalsifiable, therefore untrusted.
- Every feature tiered "standard" on a repo full of new aggregates — tier inflation to dodge
  the doc; the audit (04) should flag it.
- A review that only ever approves — if no design doc has ever been changed by review, the
  review is theater.
